## 18. 今回のデプロイ構成

### 18.1 全体像

```
         Internet
            │ HTTP(80)
            ▼
┌─ VPC 10.0.0.0/16 ──────────────────────────────┐
│ ┌─ パブリックサブネット 10.0.0.0/24 (1a) ────┐ │
│ │ EC2 t3.micro (Amazon Linux 2023, x86_64)  │ │
│ │  ├ 【ホスト】nginx                          │ │
│ │  │   ├ /      → /var/www/dist/  （React）  │ │
│ │  │   └ /api/  → 127.0.0.1:8080            │ │
│ │  └ 【Docker】backend コンテナ ×1           │ │
│ └────────────────┬──────────────────────────┘ │
│                  │ 5432                         │
│ ┌─ プライベートサブネット ─┴─────────────────┐ │
│ │ 10.0.10.0/24 (1a)   10.0.11.0/24 (1c)     │ │
│ │ RDS db.t4g.micro (PostgreSQL 18)           │ │
│ └────────────────────────────────────────────┘ │
└────────────────────────────────────────────────┘
```

サーバーは**1台だけ**です。その中でnginx（ホストに直接インストール）とバックエンドのコンテナ（1つ）が動きます。

### 18.2 フロントエンドをコンテナ化していない理由

ローカル開発では frontend もコンテナで動いていますが、あれは**Viteの開発サーバー**（ホットリロード付き）を動かすためのものです。本番で配るのは `npm run build` が生成した**HTML・CSS・JavaScriptのファイル**でしかありません。

静的ファイルを配るのにコンテナは要りません。nginxが直接読めば済みます。コンテナ化すると、本番用のDockerfileを新たに書き、コンテナ間のネットワークを設定し、その分だけ問題が起きうる箇所が増えます。得るものがないので、やっていません。

一方バックエンドはJavaの実行環境（JRE 25）を必要とするため、コンテナにする価値があります。**すでに `backend/Dockerfile` が用意されていた**ことも大きく、そのまま使えました。

### 18.3 採用しなかった構成と、その月額

構成を決めるうえで、**「使わない」という判断がそのままコスト削減になります**。

| 使わなかったもの | 本来の役割 | 月額の目安 | 使わずに済んだ理由 |
| --- | --- | --- | --- |
| **NAT Gateway** | プライベートサブネットから外部への通信 | **約$45** | RDSは接続を受けるだけで、自分から外に出ない |
| **ALB**（ロードバランサ） | 負荷分散・パスルーティング・TLS終端 | **約$18** | サーバーが1台。振り分けはnginxができる |
| **Elastic IP** | 固定のパブリックIP | 約$3.6 | 停止・起動をしなければIPは変わらない |
| **ECR** | Dockerイメージの保管庫 | 保管量に応じて | `docker save` で直接送れば足りる |
| CloudFront + Route 53 + ACM | CDNとHTTPS | 構成による | HTTPSを実装しない判断をしたため（[22章](#22-要件定義82を実装しなかった判断)） |

> **この判断が成立するのは「数日で消す」前提があるからです。** 長期運用するなら、ALBがないと証明書の更新やスケールで困りますし、Elastic IPがないと再起動のたびにURLが変わります。構成の良し悪しは、常に前提とセットで決まります。

*(金額は2026年8月時点・東京リージョンの目安です)*

## 19. VPC・サブネット・セキュリティグループ

### 19.1 VPCとサブネット

**VPC** は、AWSの中に作る自分専用のネットワークです。`10.0.0.0/16` のようにIPアドレスの範囲を決め、その中にリソースを配置します。

**サブネット** はVPCをさらに細かく区切ったものです。1つのサブネットは必ず**1つのAZ（アベイラビリティーゾーン＝データセンター群）**に属します。

今回は3つ作りました。

| サブネット | CIDR | AZ | 用途 |
| --- | --- | --- | --- |
| public | 10.0.0.0/24 | 1a | EC2 |
| private-0 | 10.0.10.0/24 | 1a | RDS |
| private-1 | 10.0.11.0/24 | 1c | **空。要件を満たすためだけに存在する** |

### 19.2 「パブリック」と「プライベート」の違いは1行だけ

サブネットに `public` / `private` という設定項目があるわけではありません。違いは**ルートテーブル**にあります。

```hcl
# パブリック用
resource "aws_route_table" "public" {
  route {
    cidr_block = "0.0.0.0/0"                      # VPC内で解決できない宛先すべてを
    gateway_id = aws_internet_gateway.main.id     # インターネットゲートウェイへ
  }
}

# プライベート用（routeブロックを書かない）
resource "aws_route_table" "private" {
  # 何も書かない。VPC内部（10.0.0.0/16 → local）への経路だけが自動で入る
}
```

**この `route` ブロックがあるかどうかだけ**が両者の違いです。無ければ外部と通信できません。

### 19.3 NAT Gatewayが要る場合と、要らない場合

プライベートサブネットの中から外に出たい場合（OSのアップデートを取得する等）は、**NAT Gateway**が必要になります。月$45程度と高価で、個人利用のAWSで最も課金事故を起こしやすいリソースです。

今回は不要でした。プライベートサブネットに置いたのがRDSだけであり、**RDSは「EC2からの接続を受ける」ことしかしない**からです。自分から外部に接続しないので、外への経路が要りません。

> ここは初学者が最も誤解しやすい箇所です。「プライベートサブネットに置いたらNAT Gatewayが要る」と機械的に覚えると、不要な月$45を払うことになります。**判断基準は「そのリソースが自分から外部に通信するかどうか」**です。

### 19.4 プライベートサブネットが2つ必要な理由

RDSは、**DBサブネットグループが2つ以上のAZにまたがること**を必須要件としています。Multi-AZ構成（待機系を別AZに持つ）に切り替えられるようにするための制約です。

今回はSingle-AZなのでRDS本体は `private-0` にしか存在しませんが、要件を満たすために `private-1` も作っています。**中身は空のままで構いません。** サブネット自体に料金はかかりません。

### 19.5 セキュリティグループ

**セキュリティグループ（SG）** は、EC2やRDSに付けるファイアウォールです。2つの重要な性質があります。

**① ステートフルである**

許可した通信の**戻りパケットは自動的に通ります**。「HTTPを受ける」ためにインバウンドで80番を許可すれば、その応答を返すためにアウトバウンドで何かを許可する必要はありません。

**② 送信元にセキュリティグループを指定できる**

```hcl
resource "aws_vpc_security_group_ingress_rule" "rds_from_ec2" {
  security_group_id            = aws_security_group.rds.id
  referenced_security_group_id = aws_security_group.ec2.id   # ← IPではなくSGを指定
  from_port                    = 5432
  to_port                      = 5432
  ip_protocol                  = "tcp"
}
```

これは「**このセキュリティグループが付いたインスタンスからの通信だけを許可する**」という意味になります。IPアドレスで書くのに比べて、

- EC2のIPが変わっても追随しなくてよい
- 「誰を許可しているのか」が意図として読める

という利点があります。AWSらしい書き方として覚えておくとよいです。

### 19.6 セキュリティグループとNACLの違い

似た仕組みに**NACL（ネットワークACL）**がありますが、次の点が異なります。

| | セキュリティグループ | NACL |
| --- | --- | --- |
| 適用される単位 | インスタンス（ENI） | サブネット |
| ステート | ステートフル（戻りは自動で通る） | ステートレス（戻りも明示的に許可が必要） |
| ルール | 許可のみ | 許可と拒否の両方 |

**通常はセキュリティグループだけで足ります。** 今回もNACLは既定のまま（全許可）で、SGだけで制御しています。

### 19.7 ここで実際に踏んだ罠

**セキュリティグループのルールの `description` に日本語を書くと、applyが失敗します。**

```
InvalidParameterValue: Invalid rule description. Valid descriptions are
strings less than 256 characters from the following set:  a-zA-Z0-9. _-:/()#,@[]+=&;{}!$*
```

AWSが許可しているのは上記のASCII文字だけで、マルチバイト文字は受け付けません。このプロジェクトはコメントを日本語で書く方針ですが、**`description` はAWSに送信される値**なので例外です。日本語で書きたい説明は、Terraformのコメント（`#`）として残してください。

## 20. EC2

### 20.1 AMIとインスタンスタイプ

**AMI（Amazon Machine Image）** は、OSとその初期状態が入ったテンプレートです。今回はAmazon Linux 2023を使っています。AWS自身が提供・保守しており、`dnf` で必要なものが揃うためです。

**AMI IDはリージョンごとに異なり、更新のたびに変わります。** そのためコードに直接書かず、その都度検索します（[docs/terraform/05-writing-the-stack.md 17章](../terraform/05-writing-the-stack.md#17-data-ソース)）。

**インスタンスタイプ** は「t3.micro」のような文字列で、性能と料金を決めます。

```
t3.micro
│ │  └── サイズ（nano < micro < small < medium ...）
│ └───── 世代
└─────── ファミリー（t = バースト可能、m = 汎用、c = 計算最適化 ...）
```

### 20.2 T系インスタンスのバーストと、その課金

T系は「**普段は低い性能で動き、必要なときだけ高い性能を出せる**」という特徴を持ちます。普段はCPUクレジットを貯め、負荷がかかるとそれを消費して性能を上げます。

問題は、**クレジットを使い切った後の挙動**です。

| モード | クレジットを使い切ると | 課金 |
| --- | --- | --- |
| **unlimited**（T3の既定） | 性能を維持する | **超過分が追加で課金される** |
| **standard** | 性能が落ちる（ベースライン以下にはならない） | 追加課金なし |

既定が `unlimited` である点が要注意です。学習用途で予期しない請求を避けたいなら、明示的に `standard` にします。

```hcl
credit_specification {
  cpu_credits = "standard"
}
```

### 20.3 キーペア

SSH接続に使う鍵です。仕組みとして重要なのは、**AWSに預けるのは公開鍵だけ**という点です。秘密鍵は手元に置いたままにします。

```bash
ssh-keygen -t ed25519 -f ~/.ssh/task-management-ec2 -N ''
```

Terraformには `file()` で公開鍵の**中身**を渡します。Terraformに鍵そのものを生成させる方法もありますが、**秘密鍵がstateに平文で保存される**ため使いません（[docs/terraform/03-state.md 12章](../terraform/03-state.md#12-stateに機密が平文で入るということ)）。

### 20.4 user_dataとcloud-init

**user_data** は、インスタンスの初回起動時に実行されるスクリプトです。実行するのは **cloud-init** という仕組みで、root権限で動きます。

性質として押さえるべき点が2つあります。

**① 一度しか実行されない。** 内容を変更しても、動いているインスタンスの中で再実行されることはありません。Terraform側で `user_data_replace_on_change = true` を指定した場合は「変更＝インスタンスの作り直し」になります（IPも変わります）。

**② ログは `/var/log/cloud-init-output.log` に残る。** 起動後に何かがおかしいときは、まずここを見ます。

```bash
# 初期化が終わるまで待つ（終わっていなければブロックする）
sudo cloud-init status --wait
```

> 起動直後にSSHして「dockerが入っていない」と戸惑うことがありますが、多くの場合はcloud-initがまだ動いている最中です。**手順の最初に `cloud-init status --wait` を置く**と、この混乱を避けられます。

### 20.5 IMDSv2

インスタンスの中からは、自分自身の情報（インスタンスID、リージョン、IAMロールの一時認証情報など）を特殊なアドレス `169.254.169.254` から取得できます。これを**インスタンスメタデータサービス（IMDS）**と呼びます。

IMDSv1は単純なGETで取得できたため、**アプリにSSRFの脆弱性があると認証情報を盗まれる**危険がありました。IMDSv2は事前にトークンを取得する方式で、これを防ぎます。

```hcl
metadata_options {
  http_tokens                 = "required"   # IMDSv2を必須にする
  http_put_response_hop_limit = 1            # コンテナ内からは到達できなくなる
}
```

### 20.6 パブリックIPv4アドレスの課金

**2024年2月から、パブリックIPv4アドレスは使用の有無にかかわらず時間課金されます**（1個あたり約$0.005/時間＝月$3.6程度）。

これはElastic IPだけでなく、**インスタンスに自動で割り当たるパブリックIPも対象**です。「EC2を止めているのに課金される」の一因になります。

### 20.7 EBSと消し忘れ

**EBS** はEC2にアタッチするブロックストレージ（仮想的なディスク）です。

```hcl
root_block_device {
  volume_size           = 16
  volume_type           = "gp3"
  delete_on_termination = true   # 既定でtrueだが明示する
}
```

`delete_on_termination` が `false` だと、**インスタンスを削除してもボリュームだけが残り、課金され続けます**。消し忘れリソースの代表例なので、明示しておくと安心です。

### 20.8 t3.microのメモリとスワップ

t3.microのメモリは**1GB**です。OS・Docker・nginx・JVM（Spring Boot）を同時に動かすと余裕がありません。

そこで、user_dataで2GBのスワップを作成しています。

```bash
dd if=/dev/zero of=/swapfile bs=1M count=2048
chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

EBS上のスワップは遅いですが、**メモリ不足でOOM Killerにプロセスを落とされるよりはまし**です。EBSの無料枠は30GBなので、この2GBは追加費用になりません。

> なお、**このマシンではGradleもViteもビルドできません**（どちらも1GB前後を要求します）。ビルドはローカルで行い、成果物だけを転送する構成にしているのはこのためです。これはDockerを使うかどうかとは無関係な、マシンの制約です。

### 20.9 実測：t3.microが使えないAZがある

東京リージョンで `t3.micro` が使えるのは **1a / 1c / 1d** で、**1bでは使えません**（2026年8月時点）。

```bash
aws ec2 describe-instance-type-offerings --location-type availability-zone \
  --filters "Name=instance-type,Values=t3.micro" --region ap-northeast-1 \
  --query 'InstanceTypeOfferings[].Location' --output text
```

AZを `"ap-northeast-1a"` のように決め打ちすると、この種の制約に引っかかったときにapplyが失敗します。`data.aws_availability_zones` で「使用可能なAZ」を問い合わせて使うほうが安全です。

## 21. RDS

### 21.1 マネージドとは何を代行してくれるのか

RDSは「AWSが運用を代行してくれるデータベース」です。具体的には、OSとDBのインストール・パッチ適用・バックアップ・障害時のフェイルオーバー・監視などを引き受けます。

EC2の中にPostgreSQLを自分で入れれば料金は安くなりますが、これらは全部自分の仕事になります。今回RDSを選んだのは、**マネージドサービスを使う経験そのものを課題の成果に含めたかった**ためです。

### 21.2 エンジンバージョンの指定

```hcl
engine_version = "18"   # メジャーバージョンだけを指定する
```

マイナーバージョンまで固定（`"18.3"`）すると、AWSがそのマイナーを廃止したときにapplyが通らなくなります。メジャーだけを指定すれば、AWSが利用可能な最新のマイナーを選びます。

利用可能なバージョンは事前に確認できます。

```bash
aws rds describe-db-engine-versions --engine postgres --region ap-northeast-1 \
  --query 'DBEngineVersions[].EngineVersion' --output text
```

### 21.3 RDSではGravitonを選べる

**Graviton** はAWSが設計したARMベースのCPUで、同等の性能で**2割ほど安い**のが特徴です。インスタンスタイプの名前に `g` が入ります（`t4g.micro`）。

ここで重要な区別があります。

| | アーキテクチャ | 理由 |
| --- | --- | --- |
| EC2 | **x86_64（t3.micro）** | ローカル（x86_64）でビルドしたDockerイメージを動かすため、揃える必要がある |
| RDS | **ARM（db.t4g.micro）** | AWS側が中で動かすため、こちらのイメージとは無関係。安いほうを選べる |

実際に接続して確認すると、ARMで動いていることがわかります。

```
PostgreSQL 18.3 on aarch64-unknown-linux-gnu
                   ^^^^^^^ ARM
```

> Dockerイメージのアーキテクチャ不一致（`exec format error`）は事故の多いポイントですが、**それが問題になるのは自分でビルドしたイメージを動かす場所だけ**です。マネージドサービスには関係ありません。ここを区別できると、安いほうを選べる場面が増えます。

### 21.4 publicly_accessible は SGの代わりではない

```hcl
publicly_accessible = false
```

これは「**RDSにパブリックIPを割り当てるかどうか**」の設定です。`false` にするとインターネットからは名前解決すらできなくなります。

ただし、これはセキュリティグループの代わりではありません。**VPC内部からの通信はSGが制御します。** 両方が必要です。

### 21.5 コストとdestroyの確実性のための設定

| 設定 | 値 | 効果 |
| --- | --- | --- |
| `multi_az` | `false` | 待機系を持たない。料金がほぼ半分になる |
| `backup_retention_period` | `0` | 自動バックアップを無効化。スナップショットの保管料が発生しない |
| `skip_final_snapshot` | `true` | **destroy時に最終スナップショットを作らせない** |
| `deletion_protection` | `false` | `true` だと `terraform destroy` が失敗する |
| `max_allocated_storage` | `0` | ストレージの自動拡張を無効化。勝手に増えて課金されるのを防ぐ |
| `performance_insights_enabled` | `false` | 監視機能。有効にすると課金対象になりうる |

> ⚠️ **`skip_final_snapshot = true` と `backup_retention_period = 0` は、本番運用では絶対にやってはいけない設定です。** データを失っても復旧できません。今回は「データはseed用SQLから再投入できる」「destroy後に課金の残骸を一切作らない」を優先した意図的な判断です。**判断の前提が変わったら、設定も変えなければなりません。**

### 21.6 同じAZに置くとデータ転送料がかからない

EC2とRDSが**別のAZ**にあると、その間の通信は「AZ間データ転送」として課金されます（往復で$0.01/GB × 2）。同一AZなら無料です。

```hcl
availability_zone = aws_subnet.private[0].availability_zone   # EC2と同じAZ
```

可用性を捨てて料金を取る判断です。Single-AZ構成では、どのみちそのAZが落ちればDBは止まります。

### 21.7 作成には5〜10分かかる

RDSの作成はEC2と比べて時間がかかります。`terraform apply` が数分間止まったように見えますが、**固まっているわけではありません**。

## 22. 要件定義8.2を実装しなかった判断

### 22.1 何を実装しなかったか

[要件定義8.2](../requirements/02-requirements.md)は、ベーシック認証とHTTPSを必須と定めています。**今回の本番環境では、その両方を実装していません。**

理由は、動作を確認したらすぐに `terraform destroy` する前提の環境であり、証明書の取得と自動更新の仕組みを用意するコストに見合わないと判断したためです。

### 22.2 これによって何が起きうるか

| リスク | 内容 |
| --- | --- |
| **誰でもデータを操作できる** | アプリ本体に認証機構がないため、認証を担う層が存在しない。URLを知る人は誰でもカードを作成・削除できる |
| 通信の盗聴・改ざん | HTTPは平文。経路上で内容を読まれ、書き換えられうる |

### 22.3 実施している緩和策

- **投入するデータをダミーデータに限定する。** 実際のタスクは入れない
- **公開期間を数日に限定する。** 確認が済み次第 `terraform destroy` する
- 人に見せる必要がない間は、`http_allowed_cidrs` を自分のIPだけに絞る

### 22.4 記録として残す

**要件を実装しないと決めたときは、その判断を記録に残すことが重要です。** 黙って実装しないと、後から見た人（半年後の自分を含む）が「実装漏れ」なのか「意図的な判断」なのか区別できません。

本プロジェクトでは以下の3か所に残しています。

- 未達を記録するIssue（クローズしない）
- [infra/README.md](../../infra/README.md) の「この構成の前提」
- 要件定義8.2そのものへの注記

### 22.5 将来実装する場合

| 方式 | 前提 | 追加コスト |
| --- | --- | --- |
| 独自ドメイン + Let's Encrypt | 使えるドメインがあること | Route 53を使うなら月$0.50程度 |
| CloudFrontのデフォルトドメイン | ドメイン不要（`xxx.cloudfront.net`） | 1TB/月まで無料枠内 |
| ALB + ACM | 独自ドメインが必要 | 月$18程度 |

**Let's Encryptを選ぶ場合、nginxをホストに直接インストールしている今回の構成が有利です。** `certbot --nginx` が証明書の取得からnginx設定の書き換え、自動更新の登録までを一手に行ってくれます（nginxをコンテナ化していると、この自動化が使えません）。

ベーシック認証は、いずれの場合もnginxの `auth_basic` で実装できます。その際は**ヘルスチェックのパスだけを認証から除外する**ことを忘れないでください（[15.3](./04-deploy-checklist.md#153-ヘルスチェックだけは認証から除外する必要がある)）。

```nginx
auth_basic           "Restricted";
auth_basic_user_file /etc/nginx/.htpasswd;

location = /actuator/health {
    auth_basic off;      # ここだけ除外する
    proxy_pass http://127.0.0.1:8080;
}
```

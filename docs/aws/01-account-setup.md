## 1. ルートユーザーとIAMユーザーの関係

AWSアカウントを作ると、まず**ルートユーザー**が1つできる。アカウント作成時に登録したメールアドレスとパスワードでサインインする主体がこれにあたる。

ルートユーザーは、そのアカウントで**できることに一切の制限がない**。EC2を起動することも、請求先クレジットカードを変更することも、アカウントそのものを解約することもできる。「管理者権限を持っている」のではなく、「権限という仕組みの外側にいる」と理解するのが近い。IAMのポリシーでルートユーザーの権限を削ることは原則できない。

これに対して **IAM（Identity and Access Management）** は、「誰が・どのリソースに・何をしてよいか」を定義するAWSの仕組みで、その中に作る作業用のログイン主体が **IAMユーザー**である。

### 1.1 なぜ日常操作でルートユーザーを使わないのか

理由は「権限が強すぎるから」の一言に尽きるが、具体的には次の3点になる。

| 観点 | ルートユーザーを使い続けた場合に起きること |
| --- | --- |
| 事故の影響範囲 | 操作ミスがアカウント解約や請求設定の変更にまで及びうる。IAMユーザーなら、付与していない権限の操作は「AccessDenied」で止まる |
| 認証情報が漏れたときの被害 | ルートの認証情報が漏れると、アカウントを乗っ取られたうえに締め出される（パスワードとMFAを変更されると本人でも入れない）。IAMユーザーのキーなら、無効化すればそこで被害が止まる |
| 誰が何をしたかの追跡 | 全部ルートで操作していると、CloudTrailのログが「ルートが操作した」としか残らない。用途ごとにIAMユーザー／ロールを分けると、後から追える |

本プロジェクトでは既にルートユーザーとは別に、AdministratorAccess相当の権限を持つIAMユーザーを作成済みである。**以降の作業はすべてこのIAMユーザーで行い、ルートユーザーは次節の「ルートでしかできない操作」が必要になったときだけ使う。**

### 1.2 ルートユーザーでしかできない主な操作

裏を返すと、以下はIAMユーザーに権限を与えても実行できない。ここだけはルートでサインインする必要がある。

- アカウントの解約（クローズ）
- アカウント名・ルートユーザーのメールアドレス・パスワードの変更
- 支払い方法の変更、サポートプランの変更
- IAMユーザーによる請求情報へのアクセス許可の設定（`Activate IAM Access`）
- 一部のS3バケットポリシー／SQSポリシーの修復（自分自身を締め出してしまった場合の復旧）

### 1.3 ルートユーザーのMFAは必須

**AWSは2025年6月以降、すべてのアカウント種別のルートユーザーにMFA（多要素認証）を要求している。** 未設定の場合、サインイン時に猶予期間つきで設定を促され、猶予が切れると設定するまで先に進めない。

MFAとは「パスワード（知っているもの）」に加えて「スマートフォンの認証アプリが生成する6桁のコード（持っているもの）」など、種類の異なる要素を組み合わせて本人確認する方式である。パスワードだけだと、それが漏れた瞬間に突破されてしまうが、MFAがあれば手元の端末も奪われない限り突破されない。

ルートユーザーの認証情報は「漏れたら終わり」の性質を持つため、**MFAは必須と考えてよい**。まだ設定していなければ、他の作業より先に済ませておくこと。

## 2. 「コンソール操作ゼロ」が原理上できない理由

本プロジェクトの方針は「マネジメントコンソール（ブラウザのGUI）をできるだけ触らず、インフラの構築とデプロイをすべてコードとCLIで行う」である。ただし、**最初の1回だけはコンソールを触らざるを得ない。** ここを知らずに進めると必ず詰まるので、先に理由を押さえておく。

### 2.1 鶏と卵の問題

AWS CLIやTerraformは、内部的にはAWSのAPIをHTTPで呼んでいる。そしてAWSのAPIは、**すべてのリクエストに署名（signature）を要求する**。署名を作るにはアクセスキーが必要で、アクセスキーを発行するAPI（`iam:CreateAccessKey`）を呼ぶには……やはり署名が必要になる。

```
アクセスキーが欲しい  →  CLIでAPIを叩く必要がある
                              ↓
                     APIを叩くには認証情報が必要
                              ↓
                     その認証情報＝アクセスキーが欲しい  （振り出しに戻る）
```

この輪を断ち切れる唯一の入口が、**ブラウザからマネジメントコンソールにサインインすること**である。コンソールのサインインはメールアドレス／ユーザー名とパスワード（＋MFA）で行われ、アクセスキーを必要としない。

> **CloudShellも「コンソール」である**：AWSにはブラウザ上で動くターミナル「CloudShell」があり、そこではAWS CLIが認証済みの状態で使える。CLIで完結させたい場合の選択肢にはなるが、CloudShellを開くにはコンソールにサインインする必要があるため、「コンソールを触らない」という条件は満たせない。

### 2.2 したがって、こう進める

コンソールでの操作を「初回1回」に閉じ込める段取りは次のとおり。

| # | 操作 | 場所 |
| --- | --- | --- |
| 1 | ルートユーザーのMFAを設定する（未設定の場合） | コンソール |
| 2 | IAMユーザーでサインインし、アクセスキーを発行する | コンソール |
| 3 | 発行したキーを手元のAWS CLIに設定する | ローカル端末 |
| 4 | 疎通確認（`aws sts get-caller-identity`） | ローカル端末 |
| 5 | 以降のリソース作成・変更・削除 | **すべてTerraform／CLI** |

3以降はコンソールを開く必要がない。予算アラート（[10章](./03-cost-management.md#10-aws-budgetsによる予算アラート)）のような「一見コンソールでやりそうな設定」も、Terraformのリソースとして書ける。

## 3. アクセスキーの発行と取り扱い

### 3.1 アクセスキーとは何か

アクセスキーは、次の2つの文字列がセットになったものである。

| 名前 | 例 | 性質 |
| --- | --- | --- |
| アクセスキーID | `AKIAIOSFODNN7EXAMPLE` | 「どのIAMユーザーか」を示す識別子。ユーザー名に相当し、これ単体が漏れても直ちに悪用はされない |
| シークレットアクセスキー | `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY` | 署名を作るための秘密の値。パスワードに相当する。**発行直後の1回しか表示されない** |

シークレットアクセスキーは再表示できない。控え忘れたら、そのキーは捨てて発行し直すことになる。

### 3.2 発行手順（コンソール）

1. IAMユーザーでマネジメントコンソールにサインインする
2. IAM → ユーザー → 対象のユーザー → **セキュリティ認証情報**タブ
3. 「アクセスキー」セクションの**アクセスキーを作成**
4. ユースケースの選択で **コマンドラインインターフェイス (CLI)** を選ぶ
5. 表示された**アクセスキーID**と**シークレットアクセスキー**を控える（この画面を閉じると二度と見られない）

手元への設定方法は [6章](./02-cli-setup.md#6-認証情報の保存場所とプロファイル) を参照。

### 3.3 取り扱いの鉄則

アクセスキーは「そのIAMユーザーとして何でもできる合鍵」である。今回のユーザーはAdministratorAccess相当なので、**漏れた場合の被害はアカウント全体に及ぶ**。以下は例外なく守る。

- **Gitのバージョン管理に載せない。** GitHubにpushされたアクセスキーは、公開・非公開を問わず数分で自動スキャンに拾われ、悪用（多くは高額な暗号通貨マイニング）に使われる実例が多数ある
- **ソースコードや設定ファイルに直書きしない。** Terraformの `.tf` に書くのも厳禁（[docs/terraform/02-install-and-workflow.md 7章](../terraform/02-install-and-workflow.md#7-aws認証情報の渡し方)）
- **チャット・Issue・スクリーンショットに貼らない。** AIツールとの会話も同じ。会話ログとして残る
- **複数人・複数用途で使い回さない。** 用途ごとにIAMユーザーまたはロールを分けると、事故のとき「どれを止めればいいか」がはっきりする

### 3.4 漏らしてしまったときの手順

慌てて削除する前に、**まず無効化**するのが定石である。無効化は即座に効き、あとから「どう使われたか」を調べる余地を残せる。

1. **無効化する** — IAM → ユーザー → セキュリティ認証情報 → 該当キーを「非アクティブ化」
2. **新しいキーを発行して切り替える** — 手元のCLI設定を新しいキーに差し替える
3. **不正利用の有無を確認する** — CloudTrailで、そのアクセスキーIDによるAPI呼び出しの履歴を確認する。身に覚えのないリージョンでのEC2起動などが典型的な兆候
4. **古いキーを削除する** — 切り替えと確認が済んでから削除する

### 3.5 ローテーション

アクセスキーは長く持つほど漏洩の機会が増える。定期的に作り直す運用を**ローテーション**と呼ぶ。手順は3.4の1〜4とほぼ同じで、「新しいキーを作る → 手元を切り替える → 動作確認 → 古いキーを無効化 → しばらく置いて削除」の順に行う。**新旧が同時に有効な期間を作る**のがコツで、いきなり古いキーを消すと切り替え漏れがあったときに何も動かなくなる。

## 4. リージョンの選び方

### 4.1 リージョンとアベイラビリティーゾーン

**リージョン（Region）** は、地理的に離れた場所にあるデータセンター群のまとまりで、`ap-northeast-1`（東京）、`us-east-1`（バージニア北部）のようなコードで識別する。

その中がさらに **アベイラビリティーゾーン（AZ）** に分かれている。AZは「電源・空調・ネットワークが独立した1つ以上のデータセンター」で、`ap-northeast-1a`、`ap-northeast-1c` のようにリージョンコード＋英字で表す。同じリージョン内のAZ同士は高速な専用線で結ばれており、**複数AZにまたがってリソースを配置することで、片方のデータセンターが落ちてもサービスを継続できる**という設計ができる。

```
リージョン ap-northeast-1（東京）
  ├─ AZ ap-northeast-1a  ← 別々の建物・別々の電源
  ├─ AZ ap-northeast-1c
  └─ AZ ap-northeast-1d
```

### 4.2 本プロジェクトは ap-northeast-1（東京）を既定にする

理由は次のとおり。

- **国内リージョンなので応答が速い。** 日本から利用するアプリなので、往復の遅延が小さいリージョンを選ぶのが素直
- **日本語の情報・事例が多い。** 学習中はこれが効く
- **データの所在が国内になる。** 個人利用のツールなので必須ではないが、迷う理由がない

#### 大阪（ap-northeast-3）ではなく東京を選ぶ理由

国内リージョンには東京のほかに**大阪（`ap-northeast-3`）**がある。関西在住であれば「大阪のほうが物理的に近いのでは」と考えたくなるが、**東京を選ぶ**。

**遅延の差は体感できない。** 東京・大阪間の往復遅延は10ms程度で、Webページの表示にかかる数百msの中に埋もれる。ミリ秒を削る用途（金融取引など）でなければ、判断材料にならない。

**決め手は、そのリージョンで使えるサービスの数である。** AWSはリージョンごとの提供サービス一覧をパラメータストアで公開しており、CLIで取得して比較できる。

```bash
for r in ap-northeast-1 ap-northeast-3; do
  printf "%s: " "$r"
  aws ssm get-parameters-by-path \
    --path "/aws/service/global-infrastructure/regions/$r/services" \
    --query 'Parameters[].Value' --output text | tr '\t' '\n' | wc -l
done
```

2026-08-26時点で実際に比較した結果は次のとおり。

| リージョン | 提供サービス数 |
| --- | --- |
| `ap-northeast-1`（東京） | 333 |
| `ap-northeast-3`（大阪） | 214 |

**東京にあって大阪に無いサービスが119件ある一方、大阪にあって東京に無いサービスは0件**だった。つまりサービスの品揃えにおいて東京は大阪の上位互換であり、大阪を選ぶことは選択肢を狭めることにしかならない。

差分119件には、小規模アプリのデプロイ先候補になりうる **App Runner**・**Lightsail** が含まれている。**構成を決める前に、リージョンの選択で候補を削ってしまう**のは避けたい。

> 大阪リージョンは2021年にフルリージョン化（3AZ）されたが、提供サービスは東京に追随しきっていない。**新しいリージョン・小さいリージョンほど品揃えが薄い**のはAWS全体に共通する傾向で、リージョン選定では物理的な距離よりこちらが効くことが多い。

### 4.3 リソースはリージョンごとに独立している

ここは最初につまずきやすい。**東京リージョンで作ったEC2インスタンスは、大阪リージョンの画面には表示されない。** CLIでも同じで、`--region` の指定（または既定リージョンの設定）が違うと「作ったはずのものが見つからない」という状態になる。

「リソースが消えた」と思ったときは、まずリージョンの取り違えを疑うこと。

### 4.4 リージョンを持たない「グローバルサービス」

一方で、リージョンという概念を持たないサービスもある。代表例は以下。

| サービス | 役割 |
| --- | --- |
| IAM | ユーザー・ロール・ポリシーの管理 |
| Route 53 | DNS（ドメイン名の名前解決） |
| CloudFront | CDN（コンテンツを世界中のエッジから配信する） |
| S3 | バケット名はグローバルに一意。ただしデータの実体はリージョンに属する |

### 4.5 us-east-1 が特別扱いされる場面

グローバルサービスに関する操作は、内部的に **`us-east-1`（バージニア北部）** を経由する設計になっているものが多い。実務で当たるのは主に次の2つ。

- **CloudFrontで使うACM証明書は、`us-east-1` で発行したものでなければならない。** 東京リージョンで証明書を作ってもCloudFrontの設定画面に出てこない
- **請求・コスト関連のデータは `us-east-1` に集約されている。** AWS BudgetsやCost Explorerを操作するときは、CLIやTerraformで `us-east-1` を指す必要がある（[10章](./03-cost-management.md#10-aws-budgetsによる予算アラート)）

Terraformでは、同じAWSプロバイダを別リージョン向けにもう1つ定義する（エイリアス）ことでこれに対応する。構成を作る段になったら、[docs/terraform/04-project-conventions.md](../terraform/04-project-conventions.md) 側であらためて扱う。

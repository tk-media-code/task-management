## 9. AWSの課金の考え方

### 9.1 従量課金であるということ

AWSは原則として**使った分だけ払う**。ここで言う「使った分」は、多くの場合**リソースが存在していた時間**であって、実際にアクセスがあったかどうかではない。

これが個人利用で最も事故につながりやすい点である。**誰もアクセスしていない深夜も、サーバーを起動したままにしていれば料金は発生し続ける。** 「動かしていないから0円のはず」という直感は通用しない。

### 9.2 3種類の「無料」を区別する

「無料枠」と一括りに語られがちだが、性質の違う3つが混ざっている。

| 種類 | 内容 | 期限 |
| --- | --- | --- |
| **Always Free** | 常に無料の範囲。30以上のサービスに設定がある（例：CloudFrontのデータ転送 1TB/月、Lambda 100万リクエスト/月、DynamoDB 25GB） | **無期限** |
| **12ヶ月無料枠** | アカウント作成から12ヶ月間だけ無料になる範囲（例：EC2 t2.micro/t3.micro 750時間/月、RDS 750時間/月、S3 5GB） | アカウント作成から12ヶ月 |
| **クレジット** | 口座に付与される金額。使用料と相殺される | 付与から一定期間 |

### 9.3 2025年7月の無料利用枠の改定

**2025年7月15日**、AWSは新規アカウントの無料利用枠の仕組みを変更した。新規アカウント作成時に、**無料プラン（Free plan）**と**有料プラン（Paid plan）**のどちらかを選ぶ形になっている。

| | 無料プラン | 有料プラン |
| --- | --- | --- |
| クレジット | $100（オンボーディング課題の達成で最大$200） | 同じ |
| 期間 | 6ヶ月、またはクレジットを使い切るまで | 期限なし |
| 期間終了時 | **アカウントが自動的に閉鎖される**（90日以内にアップグレードすればデータは復旧可能） | クレジット超過分が課金される |
| 使えるサービス | 一部のサービスに制限あり | 全サービス |
| 従来の無料枠 | — | Always Free・12ヶ月無料枠が継続 |

**本プロジェクトのアカウントは有料プランである。** したがって従来どおりのAlways Free・12ヶ月無料枠が使え、クレジットを使い切ってもアカウントが閉鎖されることはない。ただし裏を返せば、**超過分は黙って課金される**ということでもある。だからこそ次章の予算アラートを最初に仕込む。

> なお、無料プランから有料プランへの変更は6ヶ月の期間内ならいつでもできるが、**逆（有料→無料）はできない**。

## 10. AWS Budgetsによる予算アラート

### 10.1 何をするものか

**AWS Budgets** は、「今月の請求がXドルを超えそうになったらメールで知らせる」という予算監視の仕組みである。

重要なのは、**Budgetsは通知するだけで、課金を止めてはくれない**という点。AWSには「上限に達したら自動的に全部止める」というシンプルなスイッチが存在しない（止めた瞬間に本番サービスが落ちるため、そういう設計になっていない）。したがってBudgetsの役割は「気づくのが1ヶ月後の請求書ではなく、その日のうちになる」ことにある。個人の学習用途では、これだけでも被害額が2桁変わる。

### 10.2 2種類のしきい値

Budgetsでは「実績」と「予測」の両方にしきい値を置ける。両方仕掛けておくのが定石である。

| 種類 | 発火条件 | 役割 |
| --- | --- | --- |
| 実績（ACTUAL） | 実際の利用額がしきい値を超えた | 確実だが、気づくのが遅い |
| 予測（FORECASTED） | このペースだと月末にしきい値を超える見込み | 早く気づける。月初の異常な伸びを捉えられる |

例えば「月$20の予算」に対して、実績80%（$16）と予測100%（$20）で通知を設定しておくと、月の途中で異変に気づける。

### 10.3 Terraformで書ける

Budgetsはコンソールから作れるが、**Terraformの `aws_budgets_budget` リソースとしても書ける**。本プロジェクトの方針（[2章](./01-account-setup.md#2-コンソール操作ゼロが原理上できない理由)）どおり、コード側で管理する。

このとき注意が必要なのは、**請求・コスト関連のAPIは `us-east-1` に集約されている**こと（[4.5](./01-account-setup.md#45-us-east-1-が特別扱いされる場面)）。東京リージョン向けのプロバイダ設定のままでは作れないので、`us-east-1` を指すプロバイダを別途用意する必要がある。

> **IAMユーザーから請求情報が見えない場合**：「IAMユーザー／ロールによる請求情報へのアクセス」がアカウント設定で無効になっていると、AdministratorAccessを持っていても請求画面が開けない。これは**ルートユーザーでしか変更できない設定**（[1.2](./01-account-setup.md#12-ルートユーザーでしかできない主な操作)）なので、必要になったらルートでサインインして有効化する。

## 11. 課金が発生しやすい落とし穴

「作ったつもりがない」「消したつもりだった」リソースが課金され続ける、というのが典型的な事故のかたちである。金額は東京リージョンの目安（2026年8月時点の参考値）。

### 11.1 動かしていなくても課金されるもの

| リソース | 目安 | なぜ見落とすか |
| --- | --- | --- |
| **NAT Gateway** | 約$0.062/時（**月$45程度**）＋データ処理料 | 「プライベートサブネットからインターネットに出る」ために作るが、存在するだけで課金される。個人用途では最も高額になりやすい単一要素 |
| **ロードバランサ（ALB/NLB）** | 約$0.0243/時（**月$18程度**）＋処理量 | リクエストが0でも起動している限り課金される |
| **パブリックIPv4アドレス** | $0.005/時（**1個あたり月$3.6程度**） | 2024年2月から、**使用中かどうかを問わず**すべてのパブリックIPv4が課金対象になった。EC2に付いているIPも対象 |
| **Elastic IP（未割り当て）** | 同上 | 「確保したが何にも付けていない」状態が特に無駄 |
| **EBSボリューム** | 20GB gp3 で月$2程度 | EC2を終了しても、`delete_on_termination` が無効なボリュームは残り続ける |
| **EBSスナップショット / AMI** | 容量課金 | 手動で取ったバックアップは自分で消さないと残る |
| **RDS（停止中）** | ストレージ分は課金継続 | さらに、**停止したRDSは7日後に自動的に再起動する**（停止しっぱなしにはできない） |
| **CloudWatch Logs** | 保存量課金 | **既定では保持期間が「無期限」**。ログが延々と溜まる |

### 11.2 データ転送料

AWSは「入ってくる通信（イン）」は原則無料、「出ていく通信（アウト）」が課金対象という非対称な料金体系になっている。個人用途のアプリで問題になることはまれだが、**画像や動画を大量に配信する**、**無限ループするスクリプトが外部APIを叩き続ける**といったケースでは効いてくる。

CloudFrontはAlways Freeの範囲が月1TBと大きいため、静的コンテンツの配信をCloudFront経由にすると、この項目はほぼ無視できる水準になる。

### 11.3 消し忘れを防ぐ

- **リソースは必ずTerraformで作る。** コンソールで手作業で作ったものはTerraformの管理外（stateに存在しない）になり、`terraform destroy` しても消えずに残る。「コンソールを触らない」という方針は、手間の削減以上に**消し忘れの防止策**として効く
- **リージョンを固定する。** 使うリージョンを1つに決めておけば、確認すべき場所が1つで済む（[4.3](./01-account-setup.md#43-リソースはリージョンごとに独立している)）
- **Cost Explorerで「何にいくらかかったか」を見る習慣をつける。** 予算アラートが鳴ってからでは遅い

## 12. 「使うときだけ立てる」運用

### 12.1 IaCだからできること

Terraformで構成を書いておくと、**環境をまるごと作り直せる**。これはインフラをコード化することの最大の実利で、コスト面では次を意味する。

```
学習・確認したいとき  →  terraform apply    （数分で環境ができる）
終わったら           →  terraform destroy  （課金が止まる）
```

24時間稼働させると月$50〜60かかる構成でも、「週末に数時間だけ立てる」なら実費は1〜2ドルで済む。**コスト試算の「月額」は上限であって、実際に払う額ではない。**

### 12.2 destroyで失われるもの

ただし、`terraform destroy` は本当に全部消す。以下は消える前提で設計する必要がある。

| 失われるもの | 対策 |
| --- | --- |
| **データベースの中身** | 消えて困るなら、destroy前にダンプを取るか、RDSの最終スナップショットを有効にする。本プロジェクトのデータは学習用なので、割り切って消す判断もありうる |
| **エンドポイントのURL** | ロードバランサやCloudFrontのドメイン名は作り直すと変わる。ブックマークや外部からの参照は毎回貼り直しになる |
| **手作業で入れた設定** | そもそも手作業を残さない（[11.3](#113-消し忘れを防ぐ)） |

### 12.3 destroyを安全に運用する

- **`terraform plan -destroy` で消える対象を先に確認する。** 何が消えるかを読んでから実行する
- **消えては困るリソースには `prevent_destroy` を付ける。** state保管用のS3バケットなどが該当する（[docs/terraform/04-project-conventions.md 16章](../terraform/04-project-conventions.md#16-aiにterraformを書かせるときの安全策)）
- **destroy後に本当に消えたかを確認する。** destroyが途中で失敗して一部だけ残ることがある。残骸が課金され続けるのを防ぐため、Cost Explorerで翌日の請求が0に近づいているかを見る

## 13. 現状の構成と本番のギャップ

### 13.1 いまローカルで動いているもの

`docker-compose.yml` は4つのサービスを起動している。

| サービス | 中身 | 本番でどうなるか |
| --- | --- | --- |

| `backend` | Spring Boot（Gradleの継続ビルド＋DevTools） | 本番用の `backend/Dockerfile` でビルドしたJARを実行する |

## 14. 画面とAPIの同一オリジン要件

### 14.1 コードがそういう作りになっている

`frontend/src/api/client.ts:15` に、本番構成を決定づける1行がある。

```ts
const API_BASE_URL = import.meta.env.VITE_API_BASE_URL ?? ''
```

Viteは `npm run build`（productionモード）のとき `.env.development` を読まない。したがって `VITE_API_BASE_URL` は `undefined` になり、`?? ''` によって **`API_BASE_URL` は空文字**になる。結果、APIへのリクエスト先は `/api/boards` のような**相対URL**になる。

相対URLは「いま表示しているページと同じオリジン」に向かう。つまり本番のビルド成果物は、**画面を配信しているのと同じホスト・同じポート・同じスキームで `/api/*` が応答すること**を前提にしている。

### 14.2 したがって前段に何かが要る

フロントエンドは静的ファイル（HTML/JS/CSS）、バックエンドはポート8080で動くJavaプロセスであり、この2つは別物である。これを1つのオリジンに見せるには、前段で**パスによる振り分け**を行う層が必要になる。

```
        ブラウザ
           │  https://example.com/
           ▼
    ┌──────────────────┐
    │  振り分けを行う層   │
    ├──────────────────┤
    │ /api/*  → バックエンド (8080)
    │ それ以外 → 静的ファイル (index.html等)
    └──────────────────┘
```

この「振り分けを行う層」を何で実装するかが構成の選択肢になる（リバースプロキシのコンテナ、ロードバランサのパスルーティング、CDNの複数オリジン設定など）。**選択肢の比較は課題の指示が出てから行う**が、どれを選んでも「振り分けが要る」という事実は変わらない。

### 14.3 CORSは本番では不要になる

`backend/src/main/resources/application.properties:51` の `app.cors.allowed-origins=` は**空**であり、`CorsConfig` はどのオリジンも許可しない設定になっている。

これは書き忘れではなく意図的な既定値である。同一オリジンに揃えるなら、そもそもブラウザはCORSの確認を行わないため、許可リストは空で正しい。開発時だけ `application-dev.properties` が `http://localhost:5173` を許可している。

**本番デプロイ時に `SPRING_PROFILES_ACTIVE=dev` を渡してはいけない。** 渡すと開発用のCORS許可・SQLログ出力・ヘルスチェック詳細表示がすべて有効になってしまう。本番ではプロファイルを指定せず、`application.properties` の安全側の既定値をそのまま使う。

### 14.4 SPAのルーティングに注意

React Routerを使っているため、`/boards/1` のようなURLに**ブラウザから直接アクセス**されることがある。静的ファイルの配信側は、実在しないパスへのリクエストに対して404を返すのではなく、**`index.html` を返す**設定が必要になる（いわゆるSPAフォールバック）。これを忘れると、トップページからの画面遷移は動くのに、リロードすると404になる。

## 15. ベーシック認証とHTTPSをどこで満たすか

### 15.1 要件

[要件定義8.2](../requirements/02-requirements.md#82-認証セキュリティ)で以下が決まっている。

- 本人以外がアクセスできないよう、**ベーシック認証**をかける
- ベーシック認証はIDとパスワードをBase64でエンコードして送るだけで暗号化ではないため、**HTTPSを必須**とする
- 認証情報はコードに直書きせず環境変数等で管理する
- **アプリ本体（画面・データモデル）には手を入れない**

### 15.2 アプリには実装されていない（意図的に）

`backend/build.gradle` の依存に `spring-boot-starter-security` は入っておらず、認証に関するコードも存在しない。これは実装漏れではなく、[要件定義9.1](../requirements/05-tech-stack-and-roadmap.md#91-採用する技術スタック)で「Webサーバー／リバースプロキシ／ホスティング層で行う」と決めた結果である。

つまりベーシック認証は、[14.2](#142-したがって前段に何かが要る)で必要になる「振り分けを行う層」と**同じ場所で担うことになる**。振り分けと認証を1箇所にまとめられるのは都合がよい。

### 15.3 ヘルスチェックだけは認証から除外する必要がある

ここが見落としやすい。ロードバランサやコンテナオーケストレータは、**アプリが生きているかを定期的にHTTPで確認する**。このヘルスチェック用リクエストは**ベーシック認証のヘッダーを送れない**。

したがって、認証をかける層で「ヘルスチェック用のパスだけは認証なしで通す」という除外設定が必要になる。除外しないと、ヘルスチェックが常に401で失敗し、**アプリが正常なのに「異常」と判定されて再起動を繰り返す**という状態になる。

本プロジェクトでは Spring Boot Actuator の `/actuator/health` がヘルスチェックに使える。`application.properties:25` の `management.endpoint.health.show-details=never` により、応答は `{"status":"UP"}` だけで、DB接続状況などの内部情報は出さない。**無認証で外部に晒す前提でも安全な設定になっている**ため、この1パスだけを除外すればよい。

### 15.4 HTTPSに必要なもの

HTTPSには証明書が要る。証明書の入手方法は、**独自ドメインを持っているかどうか**で変わる。

| 状況 | 取りうる方法 |
| --- | --- |
| 独自ドメインがある | ACM（AWS Certificate Manager）で無料の証明書を発行し、ロードバランサやCDNに紐づける |
| 独自ドメインがない | CDNサービスが自動で払い出すドメイン（`xxxxx.cloudfront.net` 等）を使う。証明書は最初から付いており、追加費用も設定も不要 |

**この判断は構成の選択と絡むため、課題の指示が出てから決める。** ここでは「HTTPSには証明書が要る」「ドメインの有無で方法が変わる」という2点を押さえておけばよい。

## 16. DBスキーマ管理をどうするか

### 16.1 現状は本番非推奨の設定

`backend/src/main/resources/application.properties:15`：

```properties
spring.jpa.hibernate.ddl-auto=update
```

`update` は、**アプリ起動時にJPAエンティティの定義とDBの実際のスキーマを比較し、足りないテーブル・カラムを自動で作る**という設定である。開発中はマイグレーションを書かずに進められて便利だが、同ファイルのコメント自身が本番非推奨と明記している。

### 16.2 なぜ本番で危ないのか

| 問題 | 内容 |
| --- | --- |
| 何が実行されるか事前に分からない | 生成されるDDLはHibernateの判断に委ねられ、デプロイするまで確定しない |
| 削除・型変更に対応しない | カラムを消したり型を変えたりしても `update` は追随しない。エンティティとDBが静かにずれていく |
| 巻き戻せない | 意図しない変更が入っても、元に戻す手段がない |
| 複数インスタンスで競合しうる | アプリを2台以上同時に起動すると、両方が同時にDDLを流そうとする |

### 16.3 選択肢

| 方針 | 内容 | 向いている場面 |
| --- | --- | --- |
| **Flywayを導入する** | スキーマ変更をSQLファイルとしてバージョン管理し、順番に適用する。`ddl-auto` は `validate`（定義とDBが一致しているかの検証のみ）にする | 本来あるべき姿。[要件定義9.4](../requirements/05-tech-stack-and-roadmap.md#94-品質チェックツール)でも導入検討対象として挙げられている |
| **当面 `update` のまま進める** | リスクを承知のうえで、まずデプロイを通すことを優先する | 学習用の単一ユーザーアプリで、データが消えても再投入できる場合 |

**どちらを選ぶかは、デプロイの目的（動かすことが目的か、運用まで見据えるか）による判断**なので、構成が決まる段階であらためて決める。少なくとも「今のままだと本番非推奨の設定で動かすことになる」ことは、意識したうえで選ぶこと。

## 17. コンテナイメージの前提

### 17.1 バックエンドは本番用Dockerfileが用意済み

`backend/Dockerfile` はマルチステージビルドになっている。

```dockerfile
FROM eclipse-temurin:25-jdk AS build   # ビルド用（JDK。コンパイラを含む）
...
FROM eclipse-temurin:25-jre AS run     # 実行用（JRE。実行だけなら軽い）
```

ビルド用と実行用のイメージを分けているのは、**最終的なイメージにコンパイラやソースコードを含めないため**である。イメージが小さくなるだけでなく、余計なものが入っていないぶん攻撃面も減る。

### 17.2 実行時に必要な環境変数

`application.properties` は以下のプレースホルダを持つ。値が渡されないと**起動に失敗する**（プレースホルダを解決できずアプリケーションコンテキストの初期化でエラーになる）。

| 環境変数 | 例 | 備考 |
| --- | --- | --- |
| `DB_URL` | `jdbc:postgresql://<ホスト>:5432/<DB名>` | JDBCのURL形式。ホスト名は接続先に応じて変わる |
| `DB_USERNAME` | `taskuser` | |
| `DB_PASSWORD` | — | **秘密。** イメージに焼き込まず、実行時に注入する |

`SPRING_PROFILES_ACTIVE` は**本番では指定しない**（[14.3](#143-corsは本番では不要になる)）。

`DB_PASSWORD` をどう渡すかは重要な論点で、「コンテナ定義に平文で書く」と、その定義を読める人・仕組みすべてから見えてしまう。AWSにはこれを避けるための仕組み（Secrets Manager、Parameter Store）があり、構成を作る段で使うことになる。関連して、**Terraformのstateにも機密が平文で入る**という別の問題があるので、[docs/terraform/03-state.md 12章](../terraform/03-state.md#12-stateに機密が平文で入るということ)を参照。

### 17.3 CPUアーキテクチャを揃える

Dockerイメージは**CPUアーキテクチャごとに別物**である。手元（x86_64）でビルドしたイメージは、ARM系のインスタンス（AWSのGraviton系）ではそのままでは動かない。

- 実行環境のアーキテクチャに合わせてビルドする
- あるいは `docker buildx` でマルチアーキテクチャ対応のイメージを作る

ARM系はコストが安いことが多いため、選択肢に入りやすい。「安いほうを選んだらイメージが動かない」という事故が起きやすいポイントなので、構成を決めるときにあわせて確認する。

### 17.4 フロントエンドの本番用イメージは未整備

`frontend/Dockerfile.dev` はdev serverを起動するだけで、本番では使えない。本番用には次の流れが必要になる。

1. `npm ci` で依存をインストール
2. `npm run build` で `dist/` に静的ファイルを生成（`tsc -b` による型チェックを含む）
3. その `dist/` を配信する

3の配信方法は構成次第（Webサーバーのコンテナに載せる／オブジェクトストレージに置いてCDNから配信する等）なので、**構成が決まってから作る**。ただし1〜2は共通なので、どちらに転んでも無駄にはならない。

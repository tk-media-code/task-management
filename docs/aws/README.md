# AWS 学習ドキュメント

> このドキュメントは、本プロジェクト（タスク管理アプリ）を **AWS 上にデプロイする**ために必要な、AWSというクラウドサービス側の知識をまとめた学習ノートです。
> インフラをコードとして書くツールである **Terraform** の使い方は [docs/terraform/](../terraform/README.md) で扱っており、こちらは「AWSというサービスをどう扱うか」を対象にします。
> あくまで**本プロジェクトのデプロイに必要な範囲**に絞っており、AWSの全サービスを網羅するものではありません。
> AWS・Terraformともに実戦経験がない状態を出発点として書いています。

## 1. ルートユーザーとIAMユーザーの関係

アカウント作成時にできるルートユーザーが「権限という仕組みの外側にいる」存在であること、日常操作でIAMユーザーを使う理由、ルートでしかできない操作、そしてMFAが2025年6月以降必須化されていることを解説します。

📄 詳細：[01-account-setup.md](./01-account-setup.md#1-ルートユーザーとiamユーザーの関係)

---

## 2. 「コンソール操作ゼロ」が原理上できない理由

本プロジェクトは「マネジメントコンソールを触らず、すべてコードとCLIで行う」方針ですが、**最初の1回だけはコンソールが必須**です。アクセスキーを得るにはAPIを叩く必要があり、APIを叩くにはアクセスキーが要る、という鶏と卵の構造を説明し、コンソール操作を初回1回に閉じ込める段取りを示します。

📄 詳細：[01-account-setup.md](./01-account-setup.md#2-コンソール操作ゼロが原理上できない理由)

---

## 3. アクセスキーの発行と取り扱い

アクセスキーID（識別子）とシークレットアクセスキー（発行時に1度しか表示されない秘密）の違い、発行手順、Gitやチャットに載せてはいけない理由、漏らしたときに「削除より先に無効化する」定石、そしてローテーションの手順を扱います。

📄 詳細：[01-account-setup.md](./01-account-setup.md#3-アクセスキーの発行と取り扱い)

---

## 4. リージョンの選び方

リージョンとアベイラビリティーゾーンの関係、東京リージョン（`ap-northeast-1`）を既定にする理由、**リソースはリージョンごとに独立している**という初学者がつまずきやすい性質、そしてCloudFront用の証明書や請求データが `us-east-1` に固定されている理由を解説します。

📄 詳細：[01-account-setup.md](./01-account-setup.md#4-リージョンの選び方)

📄 詳細：[02-cli-setup.md](./02-cli-setup.md#5-aws-cli-v2のインストール)

## 9. AWSの課金の考え方

「使った分だけ」の"使った分"とは**リソースが存在していた時間**であってアクセス数ではない、という従量課金の基本。性質の異なる3種類の無料（Always Free／12ヶ月無料枠／クレジット）の区別と、2025年7月の無料利用枠改定（無料プランと有料プラン）を整理します。

📄 詳細：[03-cost-management.md](./03-cost-management.md#9-awsの課金の考え方)

## 10. AWS Budgetsによる予算アラート

Budgetsは**通知するだけで課金を止めない**という前提を押さえたうえで、実績・予測の2種類のしきい値を仕掛ける方法と、Terraformで管理する際に `us-east-1` が必要になる理由を扱います。

📄 詳細：[03-cost-management.md](./03-cost-management.md#10-aws-budgetsによる予算アラート)

## 12. 「使うときだけ立てる」運用

`terraform apply` で作り、`terraform destroy` で消す運用にすれば、月額の試算は上限であって実費ではなくなります。一方でdestroyによって失われるもの（DBの中身・エンドポイントのURL）と、その扱い方を整理します。

📄 詳細：[03-cost-management.md](./03-cost-management.md#12-使うときだけ立てる運用)

## 14. 画面とAPIの同一オリジン要件

`frontend/src/api/client.ts:15` の1行によって、本番ビルドではAPIが相対URL（`/api/...`）で呼ばれます。つまり**画面とAPIを同じオリジンに見せる振り分け層が必須**であること、本番でCORSが不要になる理由、SPAのルーティングで `index.html` を返す必要があることを解説します。

📄 詳細：[04-deploy-checklist.md](./04-deploy-checklist.md#14-画面とapiの同一オリジン要件)

## 15. ベーシック認証とHTTPSをどこで満たすか

認証はアプリではなく前段の層で担う設計であること（要件定義8.2）、そして**ヘルスチェックだけは認証から除外しないと、正常なアプリが再起動を繰り返す**という落とし穴を扱います。HTTPSの証明書は独自ドメインの有無で入手方法が変わります。

📄 詳細：[04-deploy-checklist.md](./04-deploy-checklist.md#15-ベーシック認証とhttpsをどこで満たすか)

## 16. DBスキーマ管理をどうするか

`spring.jpa.hibernate.ddl-auto=update` のまま本番に出すことのリスク（何が実行されるか事前に分からない・削除に追随しない・巻き戻せない）を整理し、Flyway導入と現状維持のどちらを選ぶかの判断材料を示します。

📄 詳細：[04-deploy-checklist.md](./04-deploy-checklist.md#16-dbスキーマ管理をどうするか)

## 17. コンテナイメージの前提

`backend/Dockerfile` のマルチステージ構成、起動に必須の環境変数（`DB_URL`・`DB_USERNAME`・`DB_PASSWORD`）と本番で `SPRING_PROFILES_ACTIVE` を渡してはいけない理由、CPUアーキテクチャの不一致による事故、そしてフロントエンドの本番用イメージが未整備であることを扱います。

📄 詳細：[04-deploy-checklist.md](./04-deploy-checklist.md#17-コンテナイメージの前提)

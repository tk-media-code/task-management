## 9. stateとは何か、なぜ必要か

### 9.1 Terraformが持つ「台帳」

`terraform apply` を実行すると、Terraformはカレントディレクトリに **`terraform.tfstate`** というJSONファイルを作る。これが **state（ステート）** で、「**自分がどのリソースを作ったか**」を記録した台帳である。

```json
{
  "resources": [
    {
      "type": "aws_s3_bucket",
      "name": "example",
      "instances": [
        { "attributes": { "id": "my-bucket", "arn": "arn:aws:s3:::my-bucket", ... } }
      ]
    }
  ]
}
```

### 9.2 なぜ必要なのか

「AWSに問い合わせれば現状は分かるのだから、台帳は要らないのでは」と思えるが、stateが無いと解けない問題が2つある。

**① 自分が作ったものと、もともとあったものを区別できない**

AWSアカウントには、Terraform以外の経路で作られたリソースも存在しうる（コンソールでの手作業、他のツール、AWSが自動で作るデフォルトVPCなど）。stateが無ければ、Terraformは「このS3バケットは自分の管理対象か？」を判断できない。

結果として、**`terraform destroy` が管理外のリソースまで消す**か、逆に**自分が作ったものを消し残す**ことになる。stateは「Terraformの責任範囲はここまで」という境界線そのものである。

**② コード上の名前と、実物のIDを結びつけられない**

コードでは `aws_s3_bucket.example` という論理名で書くが、AWS側の実体は `my-bucket` という物理的なIDを持つ。この対応表がstateである。名前を変えたときに「作り直し」なのか「同じものの名前変更」なのかを判断するのも、この対応表があってこそ成り立つ。

### 9.3 stateは手で編集しない

stateはJSONなので開いて書き換えられるが、**原則として手で編集してはいけない**。整合性が壊れると、Terraformが「実在するリソースをもう一度作ろうとする」「存在しないリソースを消そうとする」といった状態になる。

どうしても操作が必要な場合は、専用のコマンド（`terraform state mv` / `terraform state rm` / `terraform import`）を使う。

## 10. ローカルstateの限界

既定では、stateは作業ディレクトリの `terraform.tfstate` に置かれる。学習の最初はこれで動くが、次の3つの問題を抱えている。

### 10.1 消えたら復旧が非常に面倒

stateを失うと、Terraformは「自分は何も作っていない」と認識する。この状態で `apply` すると**すでに存在するリソースをもう一度作ろうとして失敗**し、`destroy` しても**何も消えない**（消すべき対象を知らないため）。

復旧するには、既存のリソースを1つずつ `terraform import` で拾い直すことになる。**PCが壊れた、ディレクトリを消した、というだけでこの状態になる。**

### 10.2 共有できない

別の端末やCIから同じ環境を操作できない。stateがその1台にしか無いため。

### 10.3 同時実行を防げない

2つのプロセスが同時に `apply` すると、stateの書き込みが競合して壊れうる。1人で開発していても、「applyの途中で別のターミナルからplanした」といった形で起こりうる。

### 10.4 だからリモートに置く

これらを解決するのが**リモートバックエンド**で、AWSを使うなら **S3** が定番になる。

## 11. S3バックエンドと状態ロック

### 11.1 設定

```hcl
terraform {
  backend "s3" {
    bucket       = "example-terraform-state"   # stateを置くS3バケット
    key          = "task-management/terraform.tfstate"  # バケット内のパス
    region       = "ap-northeast-1"
    encrypt      = true                        # 保存時に暗号化する
    use_lockfile = true                         # 排他制御を有効にする
  }
}
```

これで [10章](#10-ローカルstateの限界) の3つの問題が解決する。

| 問題 | S3バックエンドでどうなるか |
| --- | --- |
| 消えたら復旧が面倒 | S3のバージョニングを有効にしておけば、壊れても前の版に戻せる |
| 共有できない | どの端末からでも同じstateを見る |
| 同時実行を防げない | `use_lockfile` によるロックで、同時実行がブロックされる |

### 11.2 `use_lockfile` — DynamoDBはもう要らない

以前は、排他制御のために**DynamoDBのテーブルを別途用意する**必要があった。現在はS3自身の条件付き書き込み（conditional writes）を使った仕組みが用意されており、**DynamoDBは不要**である。

- Terraform 1.10 で試験的に導入、**1.11 で正式版（GA）**
- `use_lockfile = true` を書くと、stateと同じ場所に `.tflock` ファイルが作られ、これがロックとして機能する
- 従来の `dynamodb_table` 引数は非推奨になっており、将来のバージョンで削除される予定

ネット上には DynamoDB を使う手順の記事がまだ大量に残っているので、**古い情報を踏まないよう注意する**。

### 11.3 鶏と卵：stateを置くバケットは誰が作るのか

「stateをS3に置く」と決めた瞬間、**そのS3バケット自体は誰が作るのか**という問題が生じる。Terraformで作ろうとしても、state置き場がまだ無い。

現実的な解き方は2つ。

| 方法 | 内容 |
| --- | --- |
| **CLIで手動作成する** | `aws s3api create-bucket` などで一度だけ作る。コンソールを触らずに済む |
| **2段階にする** | ローカルstateで「バケットを作るだけの小さなTerraform構成」を先に適用し、そのあと本体の構成でそのバケットをバックエンドに指定する |

どちらでも構わない。**このバケットだけは `terraform destroy` の対象から外す**（あるいはそもそも管理下に置かない）ことが重要で、うっかり消すと全stateを失う。

## 12. stateに機密が平文で入るということ

### 12.1 これは仕様である

stateは、作成したリソースの属性を**そのまま**記録する。したがって、RDSのマスターパスワードのような機密も**平文のJSONとして書かれる**。

```json
"attributes": {
  "username": "postgres",
  "password": "S3cretP@ssw0rd",     ← 平文
  "endpoint": "xxx.rds.amazonaws.com:5432"
}
```

`.tf` 側で `sensitive = true` を指定すると、**画面への表示は伏せられる**が、**stateには平文で入る**。これは「うっかり端末に表示しない」ための機能であって、暗号化の機能ではない。

### 12.2 したがってstateは `.env` と同格に扱う

- **Gitにコミットしない。** `.gitignore` で `*.tfstate` を除外する（[14章](./04-project-conventions.md#14-gitignoreに入れるもの)）
- **S3バックエンドでは `encrypt = true` を指定する**（保存時の暗号化）
- **バケットのパブリックアクセスをブロックし、アクセスできるIAM主体を絞る**
- **`terraform show` / `terraform state pull` / `terraform output -json` は、stateの中身をそのまま標準出力に出す。** 実行結果をログやチャットに貼らない

### 12.3 そもそもstateに入れない

より根本的な対処は、**機密をTerraformに扱わせないこと**である。手段は主に3つ。

| 方法 | 内容 |
| --- | --- |
| **AWS側に生成させる** | RDSには「マスターパスワードをSecrets Managerに自動生成・自動管理させる」オプションがある。Terraformはパスワードの値そのものを一度も受け取らないため、stateにも入らない |
| **write-only 引数 / `ephemeral` を使う** | Terraform 1.11以降で導入された仕組みで、値を実行中だけ保持し、**stateに書き込まない**。パスワードのような「保存する必要がない値」に使う |
| **アプリ実行時に外から注入する** | 値をSecrets ManagerやParameter Storeに置き、アプリ（コンテナ）が起動時に読む。Terraformは「どこから読むか」だけを設定する |

本プロジェクトのDBパスワード（[docs/aws/04-deploy-checklist.md 17.2](../aws/04-deploy-checklist.md#172-実行時に必要な環境変数)）も、構成を作る段でこのいずれかを選ぶことになる。**「stateに平文で入る」ことを知らずに設計すると、あとから直すのが面倒**なので、最初に方針を決めておく。

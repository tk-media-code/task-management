## 1. IaC（Infrastructure as Code）とは何か

### 1.1 手作業との対比

クラウド上にサーバーやデータベースを用意する方法は、大きく2つある。

| 方法 | やり方 | 問題 |
| --- | --- | --- |
| **手作業** | ブラウザでマネジメントコンソールを開き、画面をクリックして作る | 何をどう設定したかが**記録に残らない**。同じ環境をもう1つ作れない。消し忘れが起きる。他人（未来の自分を含む）に説明できない |
| **IaC** | 構成をテキストファイルに書き、ツールに実行させる | ファイルがそのまま記録になる。Gitで差分と履歴が追える。同じものを何度でも作れる |

**Infrastructure as Code（IaC）** は、インフラの構成を**コードとして記述し、バージョン管理する**考え方である。「サーバーを1台立てる」という作業を、手順書ではなくコードにする、と言い換えてもよい。

### 1.2 IaCで得られるもの

本プロジェクトの文脈で効いてくるのは次の4点。

- **再現性** — 「動いていたときの構成」がファイルとして残るので、壊しても同じものを作り直せる
- **レビューできる** — アプリのコードと同じようにPRで差分を見られる。「このPRでNAT Gatewayが増えている＝月$45増える」といった判断が事前にできる
- **消し忘れが減る** — `terraform destroy` で、作ったものを漏れなく消せる（[docs/aws/03-cost-management.md 12章](../aws/03-cost-management.md#12-使うときだけ立てる運用)）
- **AIに任せられる** — 手作業のクリック操作は指示しづらいが、コードなら書かせて、人間が差分を読んでから適用できる

### 1.3 コードにすること自体が目的ではない

一方で、IaCには「学習コストが高い」「小さな変更でも書き換えて適用する手間がかかる」という側面もある。本プロジェクトがIaCを採用するのは、課題のテーマであることに加えて、**個人利用のアプリを長く安全に運用するうえで、消し忘れと再現性の問題が実際に効いてくる**からである。

## 2. 宣言的であるということ

### 2.1 「手順」ではなく「あってほしい状態」を書く

Terraformの設定ファイルは、**手順の列挙ではなく、最終的にあってほしい状態の記述**である。これを宣言的（declarative）と呼ぶ。

```hcl
# 「S3バケットを1つ作れ」ではなく
# 「my-bucket という名前のS3バケットが存在していてほしい」と書く
resource "aws_s3_bucket" "example" {
  bucket = "my-bucket"
}
```

この違いは、**同じファイルを2回適用したときの挙動**に表れる。

| 種類 | 2回目の実行 |
| --- | --- |
| 手続き的（シェルスクリプト等） | `aws s3 mb s3://my-bucket` を2回実行すると、2回目はエラーになる |
| 宣言的（Terraform） | 「すでに存在している」と判断し、**何もしない** |

「何度実行しても結果が同じ」というこの性質を**冪等性（べきとうせい）**という。手順書を人間が実行するときの「どこまでやったか分からなくなった」という状態が、原理的に起きなくなる。

### 2.2 差分を計算して埋める

Terraformが実際にやっているのは、次の3つの突き合わせである。

```
 ①コードに書かれた「あるべき状態」
 ②stateに記録された「前回作ったときの状態」
 ③AWSに実在する「現在の状態」
            ↓
      差分を計算して、埋めるための操作だけを実行する
```

②の**state**がTerraformの中核概念で、これが無いと「自分が作ったもの」と「もともとあったもの」を区別できない。詳しくは [9章](./03-state.md#9-stateとは何かなぜ必要か) で扱う。

### 2.3 適用前に差分を確認できる

宣言的であることの実利として、**実行前に「何が起きるか」を計算して見せられる**という点がある。

```bash
terraform plan   # 何が作られ・変更され・削除されるかを表示する（実際には何もしない）
terraform apply  # 実際に実行する
```

`plan` は読むためのコマンドである。**AIにインフラを書かせる場合、この `plan` の出力を人間が読むことが唯一の安全弁になる**（[16章](./04-project-conventions.md#16-aiにterraformを書かせるときの安全策)）。

## 3. プロバイダの仕組み

### 3.1 Terraform本体はAWSを知らない

意外に思えるが、**Terraform本体にはAWSの知識が一切入っていない**。Terraformがやるのは、設定ファイルを解釈し、依存関係を並べ、差分を計算し、それを「プロバイダ」に渡すところまでである。

**プロバイダ（provider）** は、特定のサービスのAPIを呼ぶためのプラグインで、AWS用のものは `hashicorp/aws` という名前で配布されている。

```
  あなたが書く .tf ファイル
            ↓
      Terraform 本体（差分計算・依存解決）
            ↓
    AWSプロバイダ（hashicorp/aws）
            ↓
        AWS の API（HTTPS）
```

この分離のおかげで、Terraformは同じ書き方でAWS・Google Cloud・Azure・GitHub・Cloudflareなど多数のサービスを扱える。**「Terraformを覚える」と「AWSを覚える」は別の学習である**という認識は持っておくとよい。本ドキュメント群を `docs/terraform/` と [docs/aws/](../aws/README.md) に分けているのも同じ理由である。

### 3.2 プロバイダはどこから来るのか

プロバイダのバイナリは、`terraform init` を実行したときに Terraform Registry から自動でダウンロードされ、作業ディレクトリの `.terraform/` 配下に置かれる。したがって：

- `.terraform/` は**Gitにコミットしない**（数百MBになるうえ、`init` すれば復元できる）
- どのバージョンを取ってきたかは `.terraform.lock.hcl` に記録され、**こちらはコミットする**（[14章](./04-project-conventions.md#14-gitignoreに入れるもの)）

### 3.3 プロバイダには認証情報を渡す必要がある

AWSプロバイダはAWSのAPIを呼ぶので、当然ながら認証情報が要る。ただし**`.tf` ファイルに書いてはいけない**。渡し方は [7章](./02-install-and-workflow.md#7-aws認証情報の渡し方) で扱う。

## 4. Terraformと似たツールの違い

インフラをコードで扱うツールはTerraformだけではない。なぜTerraformを使うのかを、対比で押さえておく。

| ツール | 提供元 | 対象 | 書き方 |
| --- | --- | --- | --- |
| **Terraform** | HashiCorp | マルチクラウド（プロバイダ次第） | HCL（専用の設定言語） |
| **OpenTofu** | Linux Foundation | 同上 | HCL（Terraformとほぼ互換） |
| **CloudFormation** | AWS | AWSのみ | YAML / JSON |
| **AWS CDK** | AWS | AWSのみ（内部でCloudFormationを生成） | TypeScript / Python などの汎用言語 |

### 4.1 なぜTerraformを選ぶか

- **求人・学習情報の量が圧倒的に多い。** 詰まったときに答えが見つかりやすいのは、学習段階では大きな利点
- **AWS以外にも同じ知識が使える。** CloudFormationとCDKはAWS専用で、他のクラウドに移ると学び直しになる
- **本課題（RaiseTech初級編17）のテーマがTerraformである**

### 4.2 OpenTofuとの関係

2023年8月、HashiCorpはTerraformのライセンスをオープンソース（MPL 2.0）から **BUSL（Business Source License）** に変更した。これを受けてコミュニティがフォークしたものが **OpenTofu** で、現在はLinux Foundationの下で開発されている。

BUSLが制限するのは「Terraformと競合する商用サービスを提供すること」であり、**自社・個人のインフラを管理する通常の用途では従来どおり無償で使える**。本プロジェクトは後者なので、Terraformをそのまま使う。

コマンド名（`terraform` / `tofu`）と一部の機能追加を除けば書き方はほぼ同じなので、**どちらかを学べばもう一方はほぼそのまま読める**。
